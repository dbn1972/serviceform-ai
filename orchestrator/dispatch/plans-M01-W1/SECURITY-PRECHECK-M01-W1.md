# SECURITY-PRECHECK-M01-W1: design flaws found before implementation

Author: security and tenant isolation verifier (Opus, xhigh), 3 Oct 2026. Read: the five plans, envelopes,
PLAN-REVIEW-M01-W1.md (present; rulings applied below), contracts/shared/**, migrations 1759482000000 and 1759490000000,
outbox.template.sql, db/test harness, CONTRACT-REVIEW-001, TENANCY.md, SECURITY.md, constitution, migration_lint.py,
infra/local/docker-compose.yml, TI v1.0 s16/s17, AWS v1.7 s20.6. Test cases are in SF-M01-00N-negative-tests.md; this
file holds only design findings. **BLOCK** = the builder must not code the affected part until the fix is adopted or the
orchestrator rules otherwise. Severity: CRITICAL / HIGH / MEDIUM / LOW.

## Cross-cutting
| ID | Sev | Finding | Why it matters | Fix |
|---|---|---|---|---|
| X-1 | HIGH (BLOCK for P-003-2, P-002-2) | Every DML grant is made to the shared group role `sf_app`, which every component's login role joins. A grant to sf_app is a grant to all components, so Constitution #23 (no writes to another component's tables) holds only by convention. | Any compromised or buggy component can forge audit-ledger rows, mint break-glass grant rows, activate policy revisions or edit the topic registry inside a tenant it holds context for. | Per-component NOLOGIN role `sf_<component>_rw` holding that component's DML grants; each component login is `IN ROLE sf_app, sf_<component>_rw`; policies stay `TO sf_app`; sf_app itself keeps no DML grants on new tables (read-only where other components legitimately read, which is nowhere in W1). This is a role/boundary change: needs an orchestrator ruling or ADR. Interim if refused: state-machine triggers named in P-002-2 and P-003-2, with the residual recorded as UCS in each handover. |
| X-2 | HIGH | The existing db/test harness enforces RLS by `SET LOCAL ROLE sf_app` from a superuser session. | Copying it would give a superuser session_user, hide grant gaps that only appear for a real login, and break the relay guard check. X-12 already forbids it; restated because all five plans say "as sf_app". | Each suite creates its own LOGIN role per the H1 rules in each negative-test file. |
| X-3 | MEDIUM | migration_lint does not see views, materialised views, SECURITY DEFINER functions, TRUNCATE grants, policy expressions or partitions created by functions. | Each of these bypasses or weakens RLS while lint stays green. | Catalogue tests in each file (001-03..06 and equivalents) are the control; propose adding these checks to migration_lint later (scripts/gates is read-only for builders). |

## SF-M01-001 (CMP-002)

The target source and the moment `app.tenant_id` is set to it are undefined. | A target taken from input and set before the authz decision is a cross-tenant write path. | Target only from the route (`/admin/tenants/{id}/bindings`) or the stored proposal; authorise with resource.tenant_id = target before BEGIN; set_config to the target only inside the privileged tx after allow; audit with that tenant. ## SF-M01-002 (CMP-048)
| ID | Sev | Finding | Why | Fix |
|---|---|---|---|---|
| P-002-1 | CRITICAL (BLOCK for the grant publisher and any Data API use) | Ruling Q2 makes the OPA Data API the channel for break-glass grants, but OPA runs with no authentication or authorization (compose: `run --server --addr=0.0.0.0:8181`), and the plan also PUTs tenant role data through the same API in integration. | Any workload that can reach OPA can `PUT /v1/data/sf_runtime/privileged_grants/...` or rewrite `data.sf.tenants[*].roles` and grant itself any action in any tenant. This defeats the PDP for every tenant. | Run OPA with `--authentication=token --authorization=basic` and a `system.authz` policy: PEP token may only POST `/v1/data/sf/authz/decision`; grant-publisher token may only write `/v1/data/sf_runtime/**`; no token may write `/v1/policies`. Bind to localhost/sidecar. Tokens via SecretsProvider. infra/** is read-only for 002: the orchestrator must assign the compose change (or the integration suite starts OPA with these flags itself). Test 002-15. |
| P-002-2 | HIGH (BLOCK for the grant publisher) | privileged_access_record grants INSERT and UPDATE(status, approved_*) to sf_app; the plan does not say the publisher pushes only command results. | Under X-1 any sf_app session in tenant T can insert an APPROVED row with a forged approver; if the publisher syncs from rows, that becomes a live break-glass grant. | Trigger state machine: insert only REQUESTED with requested_by = current_actor_id(); approve only with approved_by = current_actor_id() != requested_by and != grantee; terminal states final. Publisher pushes only the approve command's committed result; reconciliation never promotes rows lacking the approval audit_id. Test 002-06. |
| P-002-3 | MEDIUM | Revocation is a best-effort push; if OPA is unreachable the revoked grant stays live until expiry. | TI-010 (privileged access expires and is revoked). | Revoke retries until read-back confirms, raises SecurityIncidentDetected on failure; configured maximum grant duration short. Test 002-34. |
| P-002-4 | MEDIUM | PEP does not pre-check subject vs resource tenant ("OPA decides"). | A single Rego defect becomes a cross-tenant allow; RLS covers DB rows but not side effects outside the DB. | Local deny when classification is TENANT_SCOPED and tenants differ (the only privileged path keeps tenants equal per ruling Q3). Test 002-19. |
| P-002-5 | MEDIUM | `Object.freeze(ctx)` is shallow; roles and jurisdiction arrays stay mutable. | A handler or library can change roles between authorisations. | Deep freeze. Test 002-25. |
| P-002-6 | MEDIUM | security_policy_metadata UPDATE(status) is open to sf_app. | Any component can mark a revision ACTIVE. | Trigger: only VALIDATED->ACTIVE with approved_by != published_by and a test report; single ACTIVE per bundle (partial unique index); X-1. Test 002-08. |
| P-002-7 | LOW | LocalSecretsProvider reads files by ref name; LocalKms has no environment restriction. | Path traversal; local keys in production. | Name allowlist pattern, realpath containment, refuse in UAT/PREPROD/PRODUCTION/unset. Test 002-28. |

## SF-M01-004 (CMP-038)
| ID | Sev | Finding | Why | Fix |
|---|---|---|---|---|
| P-004-1 | HIGH (BLOCK) | Relay startup guard is "skippable by an explicit test flag", and tests plan to `SET ROLE sf_outbox_publisher` from a superuser session. | A configuration switch can disable the only runtime check that keeps the cross-tenant relay off sf_app/BYPASSRLS (D-02 premise); SET ROLE tests prove nothing about a real login. | Remove the flag; guard checks session_user and current_user; tests connect as a real login in sf_outbox_publisher only. Test 004-05. |
| P-004-2 | HIGH (BLOCK for replay/discard) | Operator actions are said to run as the publisher role and write an audit event to their own outbox in the same transaction; sf_outbox_publisher has no INSERT on any outbox (template) and ruling Q2 forbids new grants, so the design cannot be built as written. No authz, MFA or reason is specified for a destructive DELETE. | An implementation would either add a grant (contract change) or drop the audit, and discard deletes events. | Audit-before-act: the operator command runs as a CMP-038 sf_app login, checks PRIVILEGED_ADMIN + MFA + reason + authz, commits the audit/outbox row first; only then the relay process applies replay/discard, conditioned on status and DLQ acknowledgement; a failed audit commit means no action. Test 004-25. |
| P-004-3 | MEDIUM | Producer helper allows platform events inside tenant-context transactions. | Tenant request paths can emit platform facts (audit, security). | Per-producer allowlist of platform event types, empty by default. Test 004-10. |
| P-004-4 | MEDIUM (frozen-contract residual) | sf_outbox_publisher holds unconditional DELETE on all outbox rows (policy USING true). | A relay defect can silently delete PENDING rows (lost events). Cannot be changed without a CCR. | Code-level predicates plus static test 004-19; queue a CCR for a restrictive DELETE policy `USING (status='PUBLISHED' OR status='DEAD_LETTERED')`. Non-blocking. |
| P-004-5 | MEDIUM | Consumer derives DB tenant context from a Kafka message; anyone able to produce to the topic acts in any tenant. | Broker-level forgery. | Kafka ACLs per topic owner (infra, record as gap); consumer checks topic tenancy class vs envelope tenant and `sf-source` against the registry snapshot. Test 004-14. |
| P-004-6 | LOW | Failure-path retry UPDATE is not stated to be lease-conditioned. | Late worker can reset a PUBLISHED row. | Condition on `lease_owner` and `status='PENDING'`. Test 004-20. |
